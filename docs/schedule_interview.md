# 部署期作息问询与自动排程

## 这一段要解决什么

系统的每日固化（daily-dream）跑在夜里，读的是「昨天」的会话转写。而「昨天」是逻辑日，日界线取决于部署者的作息——凌晨两点睡的人，他的 01:30 属于前一天；晚上十点睡的人，他的 01:30 已经是新的一天。

日界线设错的后果不是报错，是**每天都有一段工作被归到错误的日子**，且没有任何提示。故它必须在部署时问清楚，不能用默认值糊过去。

同时，排程装上不等于会跑。机器睡了、盖子合了、任务计划器默认「仅接通电源时运行」而人在用电池——三种情况都让固化静默漏掉。故装完必须探供电，并明确告诉部署者要留机，且要讲清「锁屏 / 关显示器可以，合盖不行」这条区分（见问 2）。

---

## 问询（四问，插在阶段 1 之后）

按顺序问，一次一问，不要打包成表格让人填。

**问 1 · 作息**
> 你通常几点睡、几点起？（大概就行，我用它来定"一天"的分界线——比如你两点睡九点起，那凌晨一点还算你的"今天"。）

得到两个 HH:MM。

**问 2 · 夜间留机**
> 每日固化会在你睡着后自动跑一次，大概几分钟。这需要机器开着、不进睡眠。你晚上方便让它开着吗？（笔记本要接电源；**锁屏、关显示器都行，但别合盖**。）

答"不方便"→ 见下方「不留机的退路」。

> **合盖不行，接电源也不行。** macOS 合盖默认进睡眠，接电源不解除这一条（clamshell 模式要外接显示器 + 电源 + 输入设备三者齐备）。Windows 与 Linux 的默认合盖动作同样是睡眠 / 挂起，只是可在电源设置里改。锁屏与关显示器不影响排程，可以放心用——要区分开告诉部署者，否则他会用最自然的方式（合盖）收工，然后每夜固化静默不跑，而排程、收据、job 定义全都正常，任何一处产物上都看不出来。

**问 3 · 跑完关机**
> 跑完要不要帮你关机？

答"要"→ 安装时加 `--shutdown-after`，且必须回报关机权限探测结果（macOS 通常需要配免密 sudo，否则它不会真关）。

**问 4 · 时区**
> 你的 IANA 时区名是什么？（形如 `Asia/Shanghai` / `America/New_York`，不确定的话告诉我城市，我来查。）

必须**问**，不能只靠自动探测：Windows 上探测拿不到 IANA 名，不传 `--timezone` 会让收据一直停在非 READY。且时区错了不会报错——抽取窗口按本地墙钟切，时区偏了整个窗口平移，抽出来的是拼接错的两个半天，而 `manifest.json` 里日期、条数、路径全都自洽。

## 由作息推日界线

**规则**：日界线要落在「已睡下、还没起」之间，且**尽可能靠后**。

理由不对称——切早了会把一段连续的深夜工作劈成两个逻辑日，两边都不完整；切晚（贴着起床）只是让固化早一点跑，无损。故取「起床前 1 小时」为基准，夹进 `[02:00, 06:00]`，再确认它晚于入睡至少 1 小时。

**固化时刻 = 日界线 + 30 分钟**。要读「昨天全部转写」，故必须等那个逻辑日彻底关闭。

推算由 `scripts/install_schedule.py` 执行，不要手算。几个实际落点：

| 睡 | 起 | 日界线 | 固化 |
|---|---|---|---|
| 23:00 | 07:00 | 06:00 | 06:30 |
| 02:00 | 09:00 | 06:00 | 06:30 |
| 22:30 | 05:00 | 04:00 | 04:30 |
| 21:00 | 04:00 | 03:00 | 03:30 |
| 20:00 | 03:00 | 02:00 | 02:30 |

早睡早起的人自动得到更早的日界线，这正是要的效果。

---

### 推完必须念给部署者确认

推算结果**不是内部细节**，装之前要念出来等他一句确认：

> 「按你 HH:MM 睡、HH:MM 起，我把你的『一天』切在 **HH:00**——也就是说凌晨 HH:00 之前干的活还算前一天。固化排在 **HH:MM** 跑。这两个点对吗？」

他说不对时用 `--boundary-hour HH` 显式覆盖，并让他自己确认那个点他确实不在工作。**不要跳过这一步直接装**：日界线设错不报错，只会每天把一段工作归到错误的日子，而错误发生在夜里、当时没人看着；等他发现时，错归的记录已经积了很多天。念一句话的成本，换的是这类静默错误在装机当刻就被拦住。

---

**不可行的作息会被拒绝**，不会给一个夹出来的数字糊过去。窗口被挤没（如 05:30 睡 06:00 起：日界线需 ≥06:30 又需 <06:00）时脚本报错退出，要部署者用 `--boundary-hour` 显式指定并自行确认那个点他确实不工作。

## 安装（一条命令）

```bash
# 先探供电（只读）
python3 scripts/install_schedule.py --check-power

# 装（runtime 二选一，按部署者用的 CLI）
python3 scripts/install_schedule.py \
  --runtime claude \
  --sleep 02:00 --wake 09:00 \
  --timezone Asia/Shanghai \
  --assistant-root <ASSISTANT_ROOT> \
  --smoke

# 要关机就加
  --shutdown-after
```

**两个根别混**：`--assistant-root` 指用户内容目录（装着 `MEMORY/` `USER/` `00 Focus Zone/`）；宪法层（`CLAUDE.md` / `AGENTS.md`）由它反推，两套安装并存时用 `--config-file` 显式指定。发布包里 assistant root = `<repo>/assistant`，部署后可以在任何地方。

`--smoke` 会真调一次 headless CLI 验证调用形式在本机能跑通（约一分钟）。**推荐部署时开**——它是「排程会跑成功」的唯一实证；不开则只证明命令字符串拼对了，而未登录 / 参数改名 / 权限模式被拒这些失败只在真跑时现形，且那是在夜里没人看着。单独复验用 `--smoke-only`。

排程装的不是 CLI 本身，而是包装器 `run_scheduled_dream.py`——它跑完 CLI 后追加一条结构化
凭据到 `~/.pgh/natural_runs.<runtime>.jsonl`。

凭据里的时刻是**两个字段**，不可互换：

| 字段 | 含义 |
|---|---|
| `scheduled_at` | job 定义声明的**名义触发时刻**（排程本该几点跑） |
| `fired_at` | 包装器**实际开跑**的墙钟 |

唤醒补触发时两者能差几个小时（错过的 06:30 在开机后补上），故「排程按它自己声明的时刻
在跑吗」只有 `scheduled_at` 答得上。名义时刻的来源只有 job 定义一处（与 proof 同一条注入
通道），手工跑包装器拿不到它，因此该字段在手工路径上一律留空——它若能被手工填满，就退化
成又一个 `fired_at`。验收器把两者一起写进收据的 `acceptance`（`first_run_natural_scheduled_at`
与 `first_run_natural_fired_at`，周段同理）。

已装机器升级脚本后**要重跑一次安装器**：旧 job 定义里没有名义时刻，那之后的自然运行会
写出一条空值凭据，验收保持待验并报出复位动作。旧版包装器写的、根本没有这个键的历史凭据
仍然认。

**「包装器跑过」不等于「排程自然触发过」**：手工敲一条命令也能让包装器跑起来。故安装时
每装一次生成一代 `job_generation` 与一个高熵 proof，proof 只写进那一次的 job 定义，收据
里只留 `sha256(generation\0proof)`。包装器只有在环境里拿到与收据相符的 proof 时才记
`source=os-scheduler`，否则记 `manual-wrapper`——链照跑，但不冒充自然运行。

这不防本机用户主动去 job 定义里抄 proof（同一个用户读得到自己的 LaunchAgents，本地方案
挡不住，声称能挡是自欺）。它防的是**普通手工补跑**与**陈旧状态误判**：重装换代后旧 job
留下的记录、从另一端抄来的记录、以及装完之后 job 被停用或命令被改掉，都不会再翻绿。

手工带 proof 跑一趟只能叫「包装器成功路径测试」，不得报成「首次自然排程运行已发生」。
后者只在 OS job 到点自己触发（或唤醒补触发）、且验收器出具收据之后才成立。

包装器内部的调用形式：

- `--runtime codex` → `codex exec <prompt> --sandbox workspace-write --skip-git-repo-check --ephemeral -C <root>`
- `--runtime claude` → `claude -p <prompt> --permission-mode acceptEdits --output-format text --no-session-persistence`

两端都是 headless 无人值守，prompt 以各端的原生调用式开头（`$daily-dream` / `/daily-dream`）
以确保打包的 skill 真被加载，并明确「不要问我任何问题，需要 C 级确认的写成提案」。

`--ephemeral` 与 `--no-session-persistence` 不是可选项：缺了它们，排程每夜会给自己写一份会话
转写，而次日的回放会把那份转写当成一段真实工作读进去（自我回放）。

> `codex exec --full-auto` 在 codex-cli 0.146.0-alpha.9.2 上是**已弃用**（打 warning 后仍会跑），
> 不是已移除。仍然换掉：无人值守的夜跑不该挂在一个弃用兼容层上——它哪天真被移除时的表现是
> 每夜静默失败。

三个平台各用原生调度器：macOS launchd（`~/Library/LaunchAgents/`）、Windows 任务计划程序（建完立刻改电源三项设置）、Linux systemd user timer（带 `Persistent=true`，关机错过的触发开机补跑）。

**weekly 不需要单独装**。周段是 daily-dream 的周日分支——日排程装好，周级载荷自动在周日那趟追加。

## 先落正文，再装排程

顺序是刻意的。日界线要同时写进宪法层与记忆区 canon 两处，两处必须同数。若先装排程再落正文，正文写失败时会留下一个「按新日界线跑、口径还是旧值」的排程——两边各说一套，每天有一段工作被归错日子，且没有任何运行时报错。

故：**必须落点没能全部写上时，脚本不装排程、返回非 0**。先落正文则失败时什么都还没装，天然无残留。口径行形状不认识（被人改写过）时同样拒绝，不做只替半句的部分修改。

---

## 装完必须验

三层证据，别混为一谈：

1. **装上了** —— 脚本回查 `launchctl list` / `schtasks /Query` / `systemctl is-enabled`，并核对回查到的时刻与请求一致。回查不过即**回滚**（撤掉新 job、还原正文与脚本载荷、恢复旧 job 及其原本的启用状态）并返回非 0，故不存在「装了但没验过」的中间态。
2. **会按时触发** —— 回查同时抓 enabled 状态与**下次触发时刻**，连时区（IANA 名 + UTC 偏移）一起写进收据。
3. **真跑成功** —— 只能等第一次自然运行。收据里留 `acceptance.first_run_verified` 与 `first_weekly_run_verified` 两个待验位，附核验方法。**周段最晚等到第一个周一凌晨那趟**（目标逻辑日 = 周日）。

收据按 runtime 分开写在 `~/.pgh/schedule_receipt.<runtime>.json`（日志同理，
`~/.pgh/daily-dream.<runtime>.log`）。同机装两端时共用一份会互相覆盖：后装的那端把前
一端的 `acceptance` 验收状态一起写没，卸载任一端又会删掉另一端的验收状态。首字段
`state` 是唯一结论：

| state | 含义 |
|---|---|
| `READY` | 装好、会按时触发、供电就绪、headless 已实跑通过 |
| `INSTALLED_SMOKE_NOT_RUN` | 没跑 `--smoke`，「CLI 真能被调起来」这条没有实证 |
| `INSTALLED_POWER_NOT_READY` | 装好了但机器会睡，夜里不会跑 |
| `INSTALLED_SHUTDOWN_UNAVAILABLE` | 装好了但关机不可用，跑完不会关 |

没有「装上了但 CLI 跑不通」这个状态——smoke 在启用 job 之前跑，跑不通就回滚正文并
中止，不会留下一个每夜必失败的排程。

**非 READY 一律不报「装好了」**，要念出具体待办与复位动作（处理完重跑同一条命令即可，脚本幂等）。

**退出码**：0 = `READY`；1 = 装了但非 READY，或必须落点没写上而中止；2 = 参数错。

## 不留机的退路

部署者说晚上不能留机时，不要装排程装完就算，也不要假装系统仍然完整。如实告诉他两点：

1. 当夜的固化会漏——机器睡了 / 关机 / 断网时排程跑不了。
2. **漏掉的日子由次日首个真人会话自动补**，不需要他开口：`week-sync` 查出断档后**后台自动**调 `daily-dream`，按缺的逻辑日**逐日**补、**从最早那天起**，一次一天，上限**三个有效工作日**。开跑前会念一句「昨夜固化没跑成，我在后台补 X 月 X 日」，跑完回报。目标逻辑日是周日时，那一趟自动含周段。

**这是闸，不是建议。** 漏跑发生在夜里、没有人在场；次日若只提示而等用户开口，恢复就取决于他是否注意到那行提示。漏一天不痛，连漏一周会让整套记忆系统只剩白天那半截，而这种损失是静默的。

**积压超过三个有效工作日**时：补最近的三天，并明确报出更早那些天的信号已接受丢失（不静默跳过）。要追更早的，由他显式指定日期手动跑 `daily-dream`。补跑失败**不推进探针**——探针停在断档前那天，次日首会话再试一次；推进了才是真丢。

Linux 的 systemd timer 带 `Persistent=true`，关机错过的触发在开机后还会由 OS 自己补一次，是三个平台里唯一在会话之外也有一层兜底的。

---

## 关机探测是只读的

`--shutdown-after` 时脚本用 `sudo -n -l` 查授权表，**不排一次真关机来试**。探测不该有副作用：早先的实现真排了一次 40 小时后的关机再撤销，撤销若失败机器会自己关掉而部署者不知为何。

macOS 通常没有免密 sudo，故这一项经常报 `NOT-AVAILABLE`——如实告诉部署者「跑完不会关机，只在日志留一行」，并给出 `visudo` 那一行的写法。

## 完成动作

1. 脚本落日界线正文（两处同数）→ 装排程 → 回查 → 写收据。**任一步失败如实回报，不推进**。
2. `ITERATION_LOG.md` 追加：`YYYY-MM-DD | 排程安装 · 日界线 HH:00 · 固化 HH:MM · runtime=<claude|codex> · state=<收据里的 state>`
3. 告诉部署者四件：固化几点跑、要留机、当前 `state` 与待办（若非 READY）、以及怎么改（重跑本脚本换参数即可，幂等）。
4. 提醒他首跑之后回来核 `acceptance` 两位——**别把「装好了」说成「已经在跑了」**。
